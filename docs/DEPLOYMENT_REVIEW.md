# 고객사 배포 검토 — FetchNetworkConfig 1.3.0

검토일: 2026-10-09. 대상: `dist/FetchNetworkConfig-1.3.0-win-x64.zip`과 포함 EXE, 현재 소스 및 검증 기록.

## 개선 현황 — 1.3.1

이 문서의 아래 발견 사항은 **1.3.0에 대한 검토 기록**입니다. 1.3.1에는 다음 개선을 적용했습니다.

| D2 | 동일 설명의 NIC는 모호한 후보로 표시. 고유 설명 연결도 회귀 시험 통과. |

## 판단

**현재 패키지의 일반 고객사 배포는 보완 후 진행하는 것을 권고합니다.** 분석 실패 조건 2종과 NIC 이력 오매핑을 재현했고, 패키지에 내부 검증용 고객 정보가 포함돼 있습니다. 코드 서명 및 카메라 운용 중 영향 검증도 남아 있습니다.

검토한 소스와 정적 검사에서 NIC·IP·방화벽·전원·감사 설정을 의도적으로 변경하는 호출은 발견하지 않았습니다. 이 결과가 모든 WMI 제공자·보안 제품의 내부 동작이나 카메라 운용 중 무영향까지 증명하는 것은 아닙니다.

이 검토에서는 제품 소스와 기존 배포 패키지를 수정하지 않았습니다. PC 설정 수집을 새로 실행하지 않았으며 재현 자료와 보고서만 로컬 작업 폴더에 생성했습니다.

### D1. 비어 있는 조회값을 처리하지 못함

- 수집기 `src/collectors.cpp:70`은 WMI의 `VT_EMPTY`와 `VT_NULL`을 JSON `null`로 보존합니다.
- 분석기 `src/analyzer.cpp:167`, `:522`는 필터의 `Enabled`를 바로 boolean으로 변환합니다. `:311`은 `RegistryKeyword`를 바로 string으로 변환합니다. `value(key, default)`의 기본값은 키가 없는 경우에만 적용돼, 키가 있으면서 값이 `null`이면 예외가 발생합니다.
- 동일한 정상 시험 자료에서 `Enabled=true`는 분석 종료 코드 0입니다. 이를 `null`로 바꾸고 manifest 해시를 정상 갱신하면 종료 코드 2와 `type must be boolean, but is null`이 발생하며 HTML이 생성되지 않습니다.
- `RegistryKeyword=null`도 종료 코드 2와 `type must be string, but is null`로 실패합니다.
- **현재 제공된 실제 고객 자료에서 이 오류가 관찰됐다는 의미는 아닙니다.** 제공자가 값을 반환하지 않는 경우를 처리하는 경로에 취약점이 있다는 확인입니다.

권고: 조회값의 존재·형식을 확인하는 공통 접근 함수를 사용하고, 미수집/미지원/미해석을 표시하면서 나머지 보고서를 생성합니다. 알 수 없는 필터 활성값을 비활성으로 단정하지 않아야 합니다. 해당 두 조건을 회귀 시험에 추가합니다.

### D2. 동일 모델 NIC의 링크 이력을 잘못 표시할 수 있음

- `src/analyzer.cpp:365`는 이벤트 XML의 Data 값과 NIC 설명을 비교하고, 일치하는 NIC를 순서대로 덮어씁니다. 설명이 같은 NIC가 여러 개면 마지막 NIC를 선택합니다.
- 설명이 `Shared NIC description`으로 같은 NIC 1·NIC 2와 그 설명만 포함한 링크 분리 이벤트를 만들었습니다. 이벤트에는 둘을 구별할 GUID/MAC 등 식별자가 없습니다.
- 실제 배포 EXE가 생성한 HTML의 링크 이력은 **NIC 2 / 분리 1건**으로 표시됩니다. NIC 2로 확정할 근거가 없는 기록입니다.
- NIC 상세 설정·필터·드라이버 카드의 GUID 기반 연결과는 별도의 경로입니다. 이 문제는 **링크 이력 집계**에 해당합니다. 기존 실제 자료의 서로 구별되는 NIC 설명을 모두 잘못 매핑했다는 뜻은 아닙니다.

권고: 설명 일치는 후보가 정확히 하나일 때만 사용합니다. 후보가 여러 개면 원본 설명과 후보 목록을 보존해 “모호/미매핑”으로 집계합니다. 이벤트에 신뢰할 수 있는 고유 식별자가 있을 때만 해당 NIC와 연결합니다.

### D3. 정상 수집 허용 범위와 분석 한도가 불일치

- `src/common.cpp:261`: 사용자 로그 최대 16개 허용.
- `src/events.cpp:209`: 각 사용자 로그 최대 16 MiB 복사.
- 따라서 사용자 로그만 **256 MiB**입니다. 여기에 snapshot, 이벤트, SetupAPI, 타임라인 등의 증거 파일이 추가됩니다.
- `src/analyzer.cpp:12`, `:241`, `:257`의 분석 한도는 전체 증거/압축 해제 자료 **256 MiB**입니다. 수집/패키징에는 이와 일치하는 전체 예산이 없습니다(`src/report.cpp:155` 이후).
- 16 MiB 로그 16개와 작은 정상 snapshot/manifest로 만든 시험 ZIP은 약 1.12 MiB로 압축되지만, 해제 증거가 268,436,442바이트여서 배포 EXE가 종료 코드 2와 `ZIP decompression limit exceeded`로 거부했습니다.
- 이것은 수집기가 허용한 **크기를 모사한 합성 시험**입니다. 고객 PC에서 16개 로그를 실제로 수집한 시험은 아닙니다. 무옵션 기본 실행에서 이 정확한 조건이 항상 발생한다는 뜻도 아닙니다.

권고: 수집·분석의 파일/전체/레코드 한도를 함께 설계합니다. 사용자 로그 본문처럼 HTML에서 사용하지 않는 자료는 스트리밍 무결성 검증을 검토하고, 수집량을 제한한다면 제한 사실과 누락 범위를 명시합니다. 단순히 분석기 한도를 크게 높이는 방식은 고객 분석 PC의 메모리 부하를 함께 평가해야 합니다.

### D4. 실행 허용 정책과 배포 식별 정보

- `Get-AuthenticodeSignature` 결과: **NotSigned**.
- Windows 파일 속성의 FileVersion/ProductVersion/CompanyName은 비어 있습니다. `--version` 출력과 별도의 파일 메타데이터 문제입니다.
- 고객 PC의 실행 허용 정책에 따라 EXE나 동일 EXE의 수집용 자식 프로세스가 실행되지 않을 수 있습니다. Microsoft는 Smart App Control에서 알려지지 않은 미서명 코드를 기본적으로 차단한다고 설명합니다. 실제 적용 여부는 고객 환경에 따라 다릅니다. [Microsoft Smart App Control](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/overview)
- 현재 SHA-256 파일은 손상 확인 수단이며 배포자의 신원을 인증하는 서명을 대신하지 않습니다.

권고: 회사 명의의 코드 서명·타임스탬프와 VERSIONINFO를 추가하고, 고객 IT의 기존 실행 허용 절차로 확인합니다. 최종 서명된 EXE를 기준으로 해시와 ZIP을 생성합니다. 현재 빌드 CI 및 패키징 스크립트에는 서명 여부를 필수 확인하는 단계가 없습니다.

### D5. 내부 검증 정보가 고객용 패키지에 포함됨

- `tools/package.ps1:13`, `:16`은 개발용 README와 `docs/VALIDATION.md`를 그대로 포함합니다. CMake install 구성도 동일합니다.
- 실제 ZIP의 README 86행에 개발자의 사용자명과 전체 작업 경로 및 특정 증거 폴더명이 있습니다.
- 실제 ZIP의 VALIDATION 41·42·59·68행에 실제 고객 PC 이름, NIC 이력 횟수, 드라이버·설정 검증 내용이 있습니다. 다른 고객에게 전달할 필요가 없는 정보입니다.
- **원본 고객 로그와 분석 결과 파일 자체는 이 배포 ZIP에 포함되지 않았습니다.** 문제는 함께 배포하는 문서입니다.

권고: 고객용 사용 안내와 내부 검증 기록을 분리합니다. 사용 예는 일반적인 경로로 바꾸고, 배포용 검증 요약에는 익명화한 결과만 포함합니다. 패키지 생성 후 포함 파일뿐 아니라 문서 내용도 확인합니다.

### D6. 설정 무변경·운용 영향에 대한 검증 범위

- 기존 자료에는 사용자가 관리자 권한으로 수행한 실제 수집 결과 두 개가 있습니다. 실행 가능성은 확인됐지만, **최종 1.3.0 제품 EXE의 관리자 수집 전후 설정 비교**와 카메라 운용 영향 측정은 별도 근거가 없습니다.
- 현재 검증 문서의 “관리자 전체 수집 미검증” 표현은 실제 결과가 추가된 상황과 구분해 갱신할 필요가 있습니다. 실행 성공과 전후 동일성 검증은 다른 항목입니다.
- Windows 10 x64 및 고객 대상 OS/NIC/드라이버 조합의 호환성 검증이 남아 있습니다.
- 자식 프로세스의 192 MiB·작업별 30초·전체 수집 5분 제한은 있지만, **WMI 제공자 프로세스와 부모의 보고서/ZIP 생성까지 포함한 전체 자원 상한은 아닙니다**(`src/worker.cpp:18`, `:113`, `:130`).
- 기존 고객 자료에서 System 채널 시간 초과가 확인됐습니다. 가능한 증거는 보존되고 partial로 표시되므로, 종료 코드 1도 수집 결과 전달 대상으로 안내해야 합니다. 30일 요청이 30일 전체 이력 보존을 보장하지 않습니다.

권고: 시험 장비에서 최종 배포 파일로 관리자 수집 전후 비교, 파일/레지스트리/네트워크 동작 관찰, 카메라 프레임 손실·연결·CPU·메모리·디스크 영향을 확인합니다. 실행 흔적과 자원 사용까지 포함한 “PC에 어떠한 변화도 없음”으로 표현하지 않고 읽기 전용 계약의 보장 범위를 정확히 안내합니다.

## 확인한 양호 항목

- CTest 2/2 통과, `tools/verify_safety.py` 정적 읽기 전용 API 검사 통과.
- 배포 ZIP CRC와 ZIP SHA-256 일치. 배포 EXE와 Release 빌드 파일 일치 확인.
- x64 콘솔 실행 파일이며 Windows 시스템 DLL만 동적 의존. 별도 VC 런타임 설치 의존성이 없습니다.
- PE의 ASLR(Dynamic base/High Entropy VA), DEP(NX), CFG 옵션 확인.
- 자동 권한 상승 없이 수집에는 관리자 토큰을 요구하고, 분석은 일반 권한으로 수행합니다.
- 기존 파일을 덮어쓰지 않는 출력, 로컬 경로 제한, 입력 증거 무결성 검증, XML DTD/외부 resolver 차단, HTML escape 및 외부 리소스 차단 구현이 있습니다.
- 고객 원본 증거가 배포 ZIP에 혼입되지 않았고 서드파티 라이선스 파일은 포함돼 있습니다.

기존 테스트 통과와 이번 재현 오류는 동시에 성립합니다. 기존 테스트가 이번 조건들을 검사하지 않으므로 통과 사실만으로 배포 준비 완료라고 판단할 수 없습니다.

## 권장 완료 순서

1. D1의 조회값 예외 처리와 D2의 모호한 NIC 매핑을 수정하고 회귀 시험 추가.
2. D3의 수집·분석 한도 일치 및 경계 조건 확인.
3. D5의 고객용 문서 분리·익명화.
4. D4의 버전 메타데이터·서명·최종 패키지 검증.

현장 안내에는 관리자 콘솔, 쓰기 가능한 기존 로컬/외장 폴더, 종료 코드 0/1/2/3, partial 결과 전달 방법, 결과 자료의 보관·전달 방법을 포함합니다. 진단 ZIP은 암호화 기능이 없고 PC 식별·네트워크·경로·이벤트 정보가 포함되므로 고객이 허용한 저장·전달 수단을 사용합니다.
